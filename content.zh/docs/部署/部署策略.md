# 软件部署和部署策略

## 一、什么是软件部署？

**部署（Deployment）** 是指将开发好的软件发布到服务器/生产环境，让用户可以访问和使用的过程。

核心目标：

- ✅ **零停机**（Zero Downtime）：用户无感知地完成更新
- ✅ **快速回滚**：出问题能立刻恢复到上一个版本
- ✅ **风险可控**：新版本问题只影响部分用户，而非全部

---

## 二、常见部署策略对比

### 1. 重建部署（Recreate）

**流程：** 先停掉旧版本 → 再启动新版本

```
旧版本 [停止] → 新版本 [启动]
```

- ✅ 简单直接，无需额外资源
- ❌ **有停机时间**，用户会感知到中断
- 适用：开发/测试环境，或允许短暂停机的场景

---

### 2. 滚动更新（Rolling Update）

**流程：** 逐步替换旧实例，每次更新一部分

```
[旧][旧][旧][旧]
[新][旧][旧][旧]  ← 逐步替换
[新][新][旧][旧]
[新][新][新][新]
```

- ✅ **无停机**，平滑过渡
- ✅ 不需要额外的服务器资源
- ❌ 过渡期新旧版本**同时存在**，可能有兼容性问题
- ❌ 回滚较慢（需要反向滚动）
- 适用：Kubernetes 默认策略，大多数 Web 服务

---

### 3. 蓝绿部署（Blue-Green Deployment）

**流程：** 同时维护两套完全相同的环境，切换流量

```
用户流量
   ↓
[负载均衡器]
   ↓
[蓝环境 v1.0] ← 当前生产
[绿环境 v2.0] ← 新版本（待切换）

切换后：
[负载均衡器] → [绿环境 v2.0] ✅
[蓝环境 v1.0] 保留备用（快速回滚）
```

- ✅ **瞬间切换**，零停机
- ✅ **回滚极快**：只需把流量切回蓝环境
- ❌ 需要**双倍服务器资源**
- ❌ 数据库迁移需要特别处理（新旧版本共用 DB）
- 适用：对稳定性要求极高的生产环境

---

### 4. 金丝雀发布（Canary Release）

**流程：** 先将新版本发布给一小部分用户，验证无误后逐步扩大

```
100% 用户
├── 95% → 旧版本 v1.0
└──  5% → 新版本 v2.0 ← 金丝雀

验证通过后：
├── 50% → v1.0
└── 50% → v2.0

全量发布：
└── 100% → v2.0
```

> 名字来源：矿工用金丝雀检测矿井毒气，金丝雀先死说明有危险。

- ✅ **风险最小**，问题只影响少数用户
- ✅ 可以做 A/B 测试，收集真实用户反馈
- ❌ 需要流量路由能力（Nginx、Istio、Kubernetes Ingress）
- ❌ 新旧版本长期共存，运维复杂度高
- 适用：大型互联网公司（Google、Facebook 标配）

---

### 5. A/B 测试部署（A/B Testing）

与金丝雀类似，但目的不同：

| 对比项   | 金丝雀发布   | A/B 测试                           |
| -------- | ------------ | ---------------------------------- |
| 目的     | 验证稳定性   | 验证业务效果（二者都行，哪种更好） |
| 流量分配 | 按比例随机   | 按用户特征（地区、设备等）         |
| 关注指标 | 错误率、性能 | 转化率、点击率                     |

---

### 6. 影子部署（Shadow Deployment）

**流程：** 新版本接收真实流量的**副本**，但不返回结果给用户

```
用户请求 → [旧版本] → 返回给用户
              ↓ 复制流量
           [新版本] → 结果丢弃（仅用于测试）
```

- ✅ 用真实流量测试新版本，完全不影响用户
- ❌ 成本高，实现复杂
- 适用：对数据一致性要求极高的金融、支付系统

## 三、策略选择指南

| 策略       | 停机时间 | 资源消耗 | 回滚速度 | 风险 | 适用场景         |
| ---------- | -------- | -------- | -------- | ---- | ---------------- |
| 重建部署   | 有       | 低       | 快       | 高   | 开发/测试环境    |
| 滚动更新   | 无       | 低       | 中       | 中   | 通用生产环境     |
| 蓝绿部署   | 无       | 高（2x） | 极快     | 低   | 高可用生产环境   |
| 金丝雀发布 | 无       | 中       | 中       | 极低 | 大规模互联网服务 |
| 影子部署   | 无       | 高       | —        | 极低 | 金融/支付系统    |

## 四、关键概念补充

### 回滚（Rollback）

- 部署出问题时，快速恢复到上一个稳定版本
- 蓝绿部署回滚最快（切流量），滚动更新回滚最慢

### 健康检查（Health Check）

- 部署后自动检测新实例是否正常运行
- 常见方式：HTTP `/health` 接口返回 200
- Kubernetes 中分为 `livenessProbe`（存活探针）和 `readinessProbe`（就绪探针）

### 特性开关（Feature Flag）

- 代码已部署，但功能通过开关控制是否开启
- 可以做到**部署与发布分离**
- 工具：LaunchDarkly、Unleash

### CI/CD 流水线

```
代码提交 → 自动构建 → 自动测试 → 自动部署（到测试环境）→ 手动审批 → 部署到生产
```

## 五、面试常见问题

**Q: 蓝绿部署和金丝雀发布有什么区别？**  
A: 蓝绿是全量切换（瞬间从 v1 切到 v2），金丝雀是渐进式（先 5% 再 50% 再 100%）。蓝绿回滚更快，金丝雀风险更低。

**Q: 滚动更新有什么问题？**  
A: 过渡期新旧版本同时运行，如果 API 有破坏性变更（Breaking Change），可能导致兼容性问题。解决方案：保持 API 向后兼容，或使用蓝绿部署。

**Q: Kubernetes 默认用什么部署策略？**  
A: 默认是滚动更新（RollingUpdate），可以通过 `strategy.type: Recreate` 改为重建部署。
