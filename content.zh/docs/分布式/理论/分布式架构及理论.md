## 一、分布式架构概述

### 1.1 什么是分布式架构

分布式架构是将一个大型系统拆分为多个独立的服务/节点，通过网络协作完成任务的架构模式。

**核心特点：**

- 节点之间通过网络通信
- 各节点可独立部署、扩展
- 整体对外表现为一个统一系统

**与单体架构对比：**

| 维度   | 单体架构 | 分布式架构 |
| ------ | -------- | ---------- |
| 部署   | 整体部署 | 独立部署   |
| 扩展   | 整体扩展 | 按需扩展   |
| 故障   | 全局影响 | 局部隔离   |
| 复杂度 | 低       | 高         |

### 1.2 分布式架构的挑战

- **网络不可靠**：延迟、丢包、分区
- **数据一致性**：多节点数据同步
- **部分失败**：某些节点宕机
- **并发控制**：多节点并发写入

## 二、分布式理论基础

### 2.1 数据一致性

分布式系统中，多个节点的数据副本需要保持一致。

**一致性级别（从强到弱）：**

| 级别       | 说明                       | 代表           |
| ---------- | -------------------------- | -------------- |
| 强一致性   | 所有节点同一时刻数据相同   | Zookeeper      |
| 顺序一致性 | 所有节点看到相同操作顺序   | -              |
| 最终一致性 | 经过一段时间后数据趋于一致 | DNS、Cassandra |
| 弱一致性   | 不保证一致，尽力而为       | 视频直播       |

### 2.2 CAP 定理

分布式系统**不可能同时满足**以下三个特性，最多满足其中两个：

| 字母  | 含义                              | 说明                     |
| ----- | --------------------------------- | ------------------------ |
| **C** | Consistency（一致性）             | 所有节点同一时刻数据一致 |
| **A** | Availability（可用性）            | 每个请求都能得到响应     |
| **P** | Partition Tolerance（分区容错性） | 网络分区时系统仍能运行   |

**实际选择：**

- 网络分区（P）在分布式系统中**不可避免**，因此只能在 C 和 A 之间取舍
- **CP 系统**：牺牲可用性，保证一致性（如 Zookeeper、HBase）
- **AP 系统**：牺牲一致性，保证可用性（如 Cassandra、Eureka）

### 2.3 BASE 理论

BASE 是对 CAP 中 AP 方案的延伸，是互联网系统的实践总结：

| 字母   | 含义                                | 说明                       |
| ------ | ----------------------------------- | -------------------------- |
| **BA** | Basically Available（基本可用）     | 允许损失部分可用性         |
| **S**  | Soft State（软状态）                | 允许数据存在中间状态       |
| **E**  | Eventually Consistent（最终一致性） | 经过一段时间后数据最终一致 |

> BASE 理论是对强一致性的妥协，用**最终一致性**换取**高可用性**。

## 三、分布式一致性协议

### 3.1 2PC（两阶段提交）

**Two-Phase Commit**，协调者与参与者之间的两阶段提交协议。

**流程：**

```
阶段一（Prepare）：
  协调者 → 所有参与者：准备提交？
  参与者 → 协调者：Yes / No

阶段二（Commit/Rollback）：
  全部 Yes → 协调者发送 Commit
  任一 No  → 协调者发送 Rollback
```

**优点：** 实现简单，保证原子性

**缺点：**

- **同步阻塞**：参与者等待期间资源被锁定
- **单点故障**：协调者宕机导致参与者永久阻塞
- **数据不一致**：Commit 消息部分发送时宕机

### 3.2 3PC（三阶段提交）

在 2PC 基础上增加 **CanCommit** 阶段，并引入**超时机制**。

**流程：**

```
阶段一（CanCommit）：询问是否可以提交
阶段二（PreCommit）：预提交，写 undo/redo 日志
阶段三（DoCommit）：正式提交
```

**改进：**

- 引入超时机制，避免永久阻塞
- 减少协调者单点故障影响

**缺点：** 仍存在数据不一致风险（网络分区时）

### 3.3 NWR 协议

用于分布式存储系统的**读写一致性**控制。

| 参数  | 含义                 |
| ----- | -------------------- |
| **N** | 数据副本总数         |
| **W** | 写操作需成功的副本数 |
| **R** | 读操作需读取的副本数 |

**一致性条件：** `W + R > N`

**例子（N=3）：**

- W=2, R=2：强一致性
- W=1, R=3：写快读慢
- W=3, R=1：写慢读快

### 3.4 Gossip 协议

**去中心化**的信息传播协议，节点随机选择邻居传播信息，最终全网同步。

**特点：**

- 无中心节点，天然容错
- 最终一致性
- 适合大规模集群状态同步

**应用：** Cassandra、Redis Cluster 节点发现

### 3.5 Paxos 协议

分布式一致性的**经典算法**，解决多节点如何就某个值达成共识。

**角色：**

| 角色               | 职责          |
| ------------------ | ------------- |
| Proposer（提议者） | 发起提案      |
| Acceptor（接受者） | 接受/拒绝提案 |
| Learner（学习者）  | 学习最终决议  |

**Basic Paxos 流程：**

```
阶段一（Prepare）：
  Proposer → Acceptor：Prepare(n)
  Acceptor → Proposer：Promise(n) 或拒绝

阶段二（Accept）：
  Proposer → Acceptor：Accept(n, value)
  Acceptor → Proposer：Accepted 或拒绝

超过半数 Acceptor 接受 → 达成共识
```

**Multi-Paxos：**

- 选出固定 Leader 作为唯一 Proposer
- 减少（后续的） Prepare 阶段（第一次需要进行选举，必须执行），提升效率
- 是 Raft 的前身

### 3.6 Raft 协议

Paxos 的**工程化简化版**，更易理解和实现。

**三种角色：**

| 角色      | 说明                         |
| --------- | ---------------------------- |
| Leader    | 唯一处理客户端请求，复制日志 |
| Follower  | 被动接收 Leader 指令         |
| Candidate | 竞选 Leader 的临时状态       |

**核心机制：**

#### Leader 选举

```
1. Follower 超时未收到心跳 → 变为 Candidate
2. Candidate 发起投票请求（RequestVote）
3. 获得超过半数票 → 成为 Leader
4. 多个 Candidate 同时竞选 → 随机超时重试
```

#### 日志复制

```
1. 客户端请求 → Leader 写入本地日志
2. Leader → 所有 Follower：AppendEntries
3. 超过半数 Follower 确认 → Leader Commit
4. Leader 通知 Follower Commit
```

#### 网络分区处理

- 分区后各自选出 Leader
- 旧 Leader 所在少数派无法提交（无法获得多数票）
- 分区恢复后，旧 Leader 发现更高 Term → 自动降为 Follower
- 少数派日志回滚，同步多数派日志

**Term（任期）：** 单调递增的逻辑时钟，用于识别过期消息

### 3.7 Lease 机制

通过**租约（时间段）**解决分布式系统中的读一致性问题。

**原理：**

- Leader 持有 Lease，Lease 有效期内可直接处理读请求
- Lease 过期前 Leader 必须续约
- 避免网络分区时出现双主

**应用：** Chubby、etcd 的**读优化**（避免每次读需要确定leader的合法性）

## 四、分布式系统设计策略

### 4.1 心跳检测机制

节点间定期发送心跳包，检测对方是否存活。

**实现方式：**

- **主动心跳**：节点主动发送心跳
- **被动心跳**：超时未收到则判定宕机

**关键参数：**

- 心跳间隔（heartbeat interval）
- 超时阈值（timeout）

**应用：** Raft 的 Leader → Follower 心跳、Zookeeper Session 心跳

### 4.2 高可用设计

**目标：** 系统在部分节点故障时仍能正常提供服务。

**核心手段：**

| 手段       | 说明                           |
| ---------- | ------------------------------ |
| 冗余备份   | 多副本，主备/多主              |
| 故障转移   | 主节点故障自动切换到备节点     |
| 无状态设计 | 服务无状态，任意节点可处理请求 |
| 健康检查   | 定期检测节点状态               |

**可用性指标（SLA）：**

| 级别    | 年不可用时间 |
| ------- | ------------ |
| 99%     | 87.6 小时    |
| 99.9%   | 8.76 小时    |
| 99.99%  | 52.6 分钟    |
| 99.999% | 5.26 分钟    |

### 4.3 容错性与负载均衡

**容错性：**

- 超时重试（Retry）
- 幂等设计（避免重复操作副作用）
- 熔断降级（快速失败）

**负载均衡策略：**

| 策略                | 说明                    | 适用场景     |
| ------------------- | ----------------------- | ------------ |
| 轮询（Round Robin） | 依次分配                | 节点性能相近 |
| 加权轮询            | 按权重分配              | 节点性能不同 |
| 随机                | 随机选择                | 简单场景     |
| 最少连接            | 选连接数最少的节点      | 长连接场景   |
| 一致性哈希          | 相同 key 路由到相同节点 | 缓存场景     |

## 五、分布式服务调用

### 5.1 服务调用实现方式

| 方式      | 协议             | 特点           |
| --------- | ---------------- | -------------- |
| HTTP/REST | HTTP             | 通用，易调试   |
| RPC       | TCP/HTTP2        | 高性能，强类型 |
| gRPC      | HTTP2 + Protobuf | 跨语言，高效   |
| 消息队列  | AMQP/Kafka       | 异步解耦       |

### 5.2 跨域调用

**问题：** 浏览器同源策略限制跨域请求。

**解决方案：**

- **CORS**：服务端设置响应头允许跨域
- **JSONP**：利用 `<script>` 标签不受同源限制（仅 GET）
- **反向代理**：Nginx 代理转发，统一域名

## 六、分布式服务治理

### 6.1 服务协调

通过**注册中心**管理服务的注册与发现。

**流程：**

```
服务启动 → 注册到注册中心
客户端 → 查询注册中心 → 获取服务地址 → 直连调用
```

**常用注册中心：**

| 组件      | 一致性       | 特点             |
| --------- | ------------ | ---------------- |
| Zookeeper | CP           | 强一致，功能丰富 |
| Eureka    | AP           | 高可用，自我保护 |
| Nacos     | CP/AP 可切换 | 国产，功能全面   |
| Consul    | CP           | 多数据中心       |

### 6.2 服务削峰

**目标：** 平滑处理流量洪峰，避免系统被压垮。

**常用方案：**

- **消息队列缓冲**：请求先入队，消费者按能力消费
- **令牌桶/漏桶**：控制处理速率
- **异步处理**：非核心逻辑异步化

### 6.3 服务降级

**目标：** 在系统压力过大时，关闭非核心功能，保障核心服务可用。

**降级策略：**

- 返回默认值/缓存数据
- 关闭非核心功能（如推荐、评论）
- 返回友好提示

**触发条件：** 手动开关、自动（超时/错误率超阈值）

### 6.4 服务限流

**目标：** 控制请求速率，防止系统过载。

**常用算法：**

| 算法     | 原理             | 特点                   |
| -------- | ---------------- | ---------------------- |
| 计数器   | 固定时间窗口计数 | 简单，有临界问题       |
| 滑动窗口 | 动态时间窗口计数 | 解决临界问题           |
| 漏桶     | 固定速率流出     | 平滑流量，无法应对突发 |
| 令牌桶   | 固定速率生成令牌 | 允许一定突发流量       |

**常用工具：** Sentinel、Guava RateLimiter、Nginx limit_req

### 6.5 服务熔断

**目标：** 当下游服务异常时，快速失败，避免级联故障。

**熔断器三种状态：**

```
关闭（Closed）→ 正常调用，统计失败率
    ↓ 失败率超阈值
打开（Open）→ 直接返回错误，不调用下游
    ↓ 超过等待时间
半开（Half-Open）→ 放行少量请求探测
    ↓ 成功 → 关闭；失败 → 重新打开
```

**常用工具：** Hystrix、Sentinel、Resilience4j

### 6.6 服务链路跟踪

**目标：** 追踪请求在分布式系统中的完整调用链路。

**核心概念：**

| 概念         | 说明                   |
| ------------ | ---------------------- |
| Trace        | 一次完整请求的全链路   |
| Span         | 链路中的一个操作单元   |
| TraceId      | 全局唯一，标识一次请求 |
| SpanId       | 标识链路中的某个操作   |
| ParentSpanId | 父操作的 SpanId        |

**Trace 模型：**

```
TraceId: abc123
  └── Span: API Gateway (SpanId: 1)
        └── Span: UserService (SpanId: 2, ParentSpanId: 1)
              └── Span: DB Query (SpanId: 3, ParentSpanId: 2)
```

**常用工具：** Zipkin、Jaeger、SkyWalking、OpenTelemetry

## 七、架构设计基本原则

> 即 **SOLID 原则** + **迪米特法则** + **合成复用原则**，共 7 大原则。

### 7.1 开闭原则（OCP）

**Open/Closed Principle**

> 对**扩展开放**，对**修改关闭**。

- 新增功能通过扩展实现，而非修改已有代码
- 通过抽象、接口、继承实现
- **目的：** 降低修改带来的风险

### 7.2 单一职责原则（SRP）

**Single Responsibility Principle**

> 一个类/模块只负责**一件事**。

- 职责越单一，变化影响越小
- 高内聚，低耦合
- **目的：** 降低类的复杂度，提高可维护性

### 7.3 接口隔离原则（ISP）

**Interface Segregation Principle**

> 客户端不应依赖它**不需要的接口**。

- 将大接口拆分为小接口
- 类只实现自己需要的接口
- **目的：** 减少不必要的依赖

### 7.4 里氏替换原则（LSP）

**Liskov Substitution Principle**

> 子类必须能**替换**父类，且程序行为不变。

- 子类可以扩展父类功能，但不能改变父类原有行为
- 是继承复用的基础
- **目的：** 保证继承的正确性

### 7.5 依赖倒置原则（DIP）

**Dependency Inversion Principle**

> 高层模块不依赖低层模块，二者都依赖**抽象**。

- 面向接口编程，而非面向实现
- 依赖注入（DI）是其典型实践
- **目的：** 降低模块间耦合

### 7.6 迪米特法则（LoD）

**Law of Demeter（最少知识原则）**

> 一个对象应尽量少了解其他对象，只与**直接朋友**通信。

- 减少对象间的直接依赖
- 通过中间层（Facade、Mediator）解耦
- **目的：** 降低系统耦合度

### 7.7 合成复用原则（CRP）

**Composite Reuse Principle**

> 优先使用**组合/聚合**，而非继承来实现复用。

- 继承是白盒复用，破坏封装性
- 组合是黑盒复用，灵活性更高
- **目的：** 降低继承带来的耦合
